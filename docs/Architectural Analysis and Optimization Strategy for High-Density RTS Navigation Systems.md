Introduction: The Scalability Problem in Modern Real-Time StrategyDeveloping engines for Real-Time Strategy (RTS) games capable of simulating over 1,000 units on expansive maps is one of the most challenging tasks in interactive entertainment engineering. Unlike FPS or RPG genres, where the active agent count rarely exceeds a few dozen, RTS requires the simultaneous management of thousands of entities, each making navigational decisions multiple times per second. An analysis of "current code" based on typical architectural patterns reveals fundamental logical issues stemming from attempts to linearly scale algorithms designed for small groups. The transition from tactical skirmishes to macro-scale battles exposes critical bottlenecks in traditional Pathfinding and Local Avoidance approaches.1The fundamental error in naive RTS implementations lies in treating units as isolated agents solving independent navigation tasks. When a player commands a group of 100 units to move to a single point, a system built on Object-Oriented Programming (OOP) and the A\* (A-Star) algorithm generates 100 nearly identical pathfinding requests. This creates massive redundant load on the CPU. Furthermore, as units converge, they begin to perceive each other as dynamic obstacles, leading to cascading path invalidation and constant recalculations. This phenomenon, often described by players as "fighting the interface," manifests as jittery movement, units getting stuck on geometry, and the formation of inefficient "conga lines" instead of dense combat formations.3To achieve fluid simulation of 1,000+ units, a paradigm shift is required from a Unit-Centric model (where each unit "thinks" for itself) to Data-Centric and Group-Centric models (where the map or squad manages data flows). This report provides a comprehensive technical analysis and roadmap for implementing Flow Fields, Hierarchical Pathfinding, Velocity-Based Obstacle Avoidance (RVO2/ORCA), and Data-Oriented Design (DOD/ECS) principles to resolve these challenges.Section 1. Theoretical Analysis of Traditional Navigation BottlenecksBefore proposing solutions, it is necessary to deconstruct the performance anatomy of a standard RTS navigation system. It consists of three main resource consumers: Global Pathfinding (route calculation), Locomotion (movement along the route), and Local Avoidance (preventing collisions with allies). In systems not optimized for mass scale, each of these components becomes a bottleneck.1.1. The $O(N^2)$ Complexity Catastrophe in Collision DetectionIn systems where units are treated as discrete physical objects with rigid boundaries, collision detection often reduces to checking every moving object against every other object to prevent overlap. For $N$ units, this results in a computational complexity of $O(N^2)$. With 1,000 units, the system is forced to perform up to 1,000,000 checks per simulation tick. Even with Spatial Partitioning methods like Quadtrees or Spatial Hashing, the constant updating of data structures for dynamic objects creates significant overhead.Logical analysis suggests that precise physical collision for every unit is an excessive and computationally unaffordable luxury. High-performance engines, such as those used in Supreme Commander 2 or StarCraft II, relax these constraints by using "soft" collisions or repulsion forces instead of rigid body physics.5 The rigid requirement that units never overlap is a logical error in large-scale simulation; allowing slight, resolvable overlaps permits the use of much cheaper force-based avoidance algorithms rather than expensive constraint solvers.1.2. The Cache Coherency Gap (AoS vs. SoA)Traditional Object-Oriented Programming (OOP) involves storing unit data in classes (e.g., class Unit { Vector3 pos; float health;... }). This layout, known as Array of Structures (AoS), is detrimental to CPU cache performance during mass updates. When the movement system iterates through 1,000 units to update their positions, the CPU loads the entire Unit object into a cache line, including data completely irrelevant to movement, such as current health, mana, unit name, or texture pointers.This results in inefficient memory bandwidth usage. If a unit object takes up 128 bytes but only 12 bytes (Vector3) are needed for position updates, the useful cache payload is less than 10%. The remaining 90% of data simply "pollutes" the cache, evicting potentially useful information. This provokes frequent cache misses, causing the CPU to idle for hundreds of cycles waiting for data from RAM. For a system with 1,000+ units, logic must operate on contiguous blocks of relevant data. Data-Oriented Design (DOD) principles dictate the use of Structure of Arrays (SoA), where all unit positions are stored in one dense array and all velocities in another. This allows the CPU to use SIMD (Single Instruction, Multiple Data) instructions, processing 4-8 units per cycle instead of one.1.3. Pathfinding Redundancy and the Dynamic Obstacle ProblemWhen a player selects a group of 50 units and assigns a destination, a naive system queues 50 separate A\* requests. Since the units start from the same area and share a common goal, 90% of the pathfinding work is duplicative.1 The A\* algorithm explores the same navigation graph nodes dozens of times, yielding nearly identical results. This is an irrational use of computational resources.Moreover, A\* returns a static list of waypoints. If a dynamic obstacle appears on the path (e.g., a constructed building or another group of units), the entire calculated path becomes invalid, requiring expensive recalculation. In a dynamic RTS environment where the situation changes every second, paths become obsolete faster than units can traverse them.2 Relying on cached static paths in a dynamic environment is a logical error; the navigation system must be continuous and reactive, not discrete and static.A separate issue is handling cases where no path exists. In standard A\*, this is the worst-case scenario: the algorithm must check all reachable graph nodes before concluding the destination is unreachable. If a player clicks on an unreachable area (e.g., an island or mountain peak), this can cause a micro-freeze (lag), as hundreds of units simultaneously trigger full graph traversals. An effective system must have mechanisms for early rejection of such requests, such as region connectivity checks.6Section 2. Macro-Optimization: Flow Field ArchitectureTo support thousands of units, the industry standard has shifted from using A\* for individual units to Flow Field (or Vector Field) architecture. This technique, popularized by Supreme Commander 2 and Planetary Annihilation, inverts the pathfinding relationship: instead of units finding a path to the goal, the goal calculates paths to all units on the map.12.1. Theoretical Foundation and the Eikonal EquationA Flow Field is a grid overlaid on the map where each cell contains a vector pointing in the optimal direction of movement toward the goal. Once such a field is generated, any number of units—whether 10 or 10,000—can navigate to the goal with zero additional pathfinding cost. Units simply read the vector from the cell beneath them and apply it to their velocity.7Generation Process: Heat PropagationGenerating a high-quality flow field mimics wave propagation. The process begins at the target cell (goal) and propagates a "wavefront" outward, assigning each map cell a cost representing the "distance" to the target. This is essentially Dijkstra's algorithm run until it covers the entire map or the required area.8The value in each cell is determined by the Eikonal equation, which describes the time it takes for a wavefront to travel through a medium. In the context of RTS, the equation takes the form:$$|\\nabla T(x)| F(x) = 1$$Where $T(x)$ is the arrival time (accumulated cost) at position $x$, and $F(x)$ is the speed of propagation (the inverse of terrain cost). For a discrete grid, the cost integration phase calculates the accumulated cost to reach the goal from any node.9Field TypeFunctionData StructureMemory ImpactCost FieldDefines static terrain difficulty (walls, swamps, roads).2D Array (Byte/Int8)Low (Static)Integration FieldStores accumulated distance to a specific goal.2D Array (Float/Int32)High (Dynamic per goal)Vector FieldStores direction vectors to the lowest-cost neighbor.2D Array (Vector2)High (Dynamic per goal)This approach solves the redundancy problem: the field calculation is performed once for the group, not for each unit. If a group is split by an obstacle, the field naturally directs parts of the group along different routes that subsequently converge, creating a "fluid flow" effect.102.2. Implementing Tiled Flow FieldsGenerating a flow field for a massive map (e.g., 8192x8192 cells) is too slow for real-time execution. A full integration field recalculation for such a map can take hundreds of milliseconds. The optimization used in Supreme Commander 2 is Hierarchical Tiling.11Hierarchical Decomposition Algorithm:Map Decomposition: The global map is divided into chunks or "tiles" (e.g., 32x32 cells).Global Graph: A high-level graph is built where each node represents a tile. Edges exist between adjacent tiles if passage is possible.Hierarchical Search: When a move order is issued, A\* is run on the high-level graph to determine the sequence of tiles needed to reach the goal (e.g., Tile A -> Tile B -> Tile C).6Local Flow Generation: Flow fields are generated only for the tiles involved in the active chain and tiles currently containing units.Flow Handoff: The vector field inside a tile directs units not to the final goal, but to the "portal" (boundary) leading to the next tile in the sequence.2This architecture reduces computational load from $O(MapSize)$ to $O(PathLength \\times TileSize)$, making the system scalable for maps of any size. Units treat the flow field as a Look-Up Table, eliminating CPU spikes associated with group movement commands.2.3. Line of Sight (LoS) SmoothingDirect Dijkstra wave propagation on a grid leads to "Manhattan" or "Chebyshev" style movement, where units move strictly at 45 or 90-degree angles, appearing unnatural and robotic. To achieve natural movement, the vector generation phase must include Line of Sight (LoS) Smoothing.11When calculating the vector for a cell, the algorithm checks if that cell has a direct line of sight to a "distant ancestor" (a neighbor with significantly lower integration cost), skipping the immediate neighbor. If the raycast to the remote node is clear, the vector points directly there. In Supreme Commander 2, this is implemented by carrying the "wavefront" of visible pixels during the integration phase, effectively "baking" line of sight into the field generation.11 This results in units choosing smooth, Euclidean paths, naturally cutting corners instead of zigzagging along grid lines.2.4. Integrating Dynamic ObstaclesA critical limitation of basic flow fields is static topology. In RTS, players build and destroy structures, altering the Cost Field. Recalculating the entire field for every change is too expensive. To solve this, a local update approach is used:Dirty Rectangles: When a building is placed, affected tiles are marked as "dirty."Local Re-integration: Dijkstra's algorithm is restarted only for the affected tiles, and changes propagate to neighbors only if the cost difference exceeds a certain threshold.13Stamp-Based Updates: Instead of pixel-by-pixel cost recalculation, a "stamp" of the building's cost is applied to the Cost Field, triggering a partial update.For temporary dynamic obstacles (like other units), flow fields are typically not updated. Instead, local avoidance (steering behaviors) is used to navigate around temporary blockers, preventing system thrashing due to constant recalculations.14Section 3. Micro-Optimization: Local Avoidance and SteeringWhile Flow Fields provide macro-direction (how to get from Base A to Base B), they do not prevent unit collisions. This is the responsibility of Local Avoidance. "Current code" likely uses simple repulsion forces or "check and wait" logic, which fail at high density (units start vibrating, getting stuck, or pushing through each other). The optimal solution lies in velocity-space algorithms.3.1. RVO2 and ORCA: The Mathematics of Collision-Free MotionThe gold standard for local avoidance in RTS is Optimal Reciprocal Collision Avoidance (ORCA), an evolution of RVO (Reciprocal Velocity Obstacles).15Conceptual FoundationUnlike standard repulsion, which pushes units apart based on current position (often causing oscillation), ORCA operates in velocity space. The algorithm assumes both colliding agents will try to avoid the collision and solves for a new velocity that guarantees no collision within a given time horizon.16Velocity Obstacle (VO): Represents the set of all velocity vectors that will result in a collision with another agent within time $\\tau$. Geometrically, this is a cone in velocity space.Reciprocity: The algorithm assumes the other agent takes half the responsibility for avoiding the collision. Agent A changes its velocity by $\\Delta V/2$, and Agent B by $-\\Delta V/2$. This eliminates the "chicken" problem where both agents dodge in the same direction.16Linear Programming: The set of permissible velocities forms a convex region bounded by linear constraints (half-planes). ORCA finds the velocity within this region closest to the unit's desired velocity (from the Flow Field).15Integration with Flow FieldsThe logical pipeline for integrating these systems is:Flow Field Query: The unit polls the grid to get Desired\_Velocity.Neighbor Search: The unit polls a spatial partition structure (Spatial Hash) to find neighbors within radius $R$.ORCA Solver: Desired\_Velocity and neighbor velocities are fed into the ORCA solver.Result: ORCA returns Safe\_Velocity.Physics Integration: Safe\_Velocity is applied to the unit's position: $Position += Safe\\\_Velocity \\times \\Delta t$.This hybrid approach ensures units follow the global path (Flow Field) while seamlessly weaving through traffic (ORCA). It prevents the "jitter" characteristic of force-based systems because the solution is mathematically stable.163.2. Handling "Sidedness" and DeadlocksA subtle logical issue in avoidance is "sidedness": agents disagreeing on which side to pass each other (left or right), leading to a "dance." ORCA solves this by introducing constraints that favor a specific side, typically determined by relative position.16However, dense crowds can still deadlock (e.g., units trying to exit a narrow chokepoint while others try to enter). Additional mechanics are applied to resolve this:Priority Systems: Assigning mass or priority classes. Heavy units (Tanks) "push" light ones (Infantry). In the solver, the light unit takes 100% of the avoidance responsibility, and the tank takes 0%.3Discomfort Fields: In the flow field, tiles occupied by static units are marked with high cost. The integration phase naturally routes new units around the cluster, treating the crowd as part of the terrain.18Section 4. System Architecture: Data-Oriented Design and ECSImplementing the above algorithms in a traditional OOP codebase will inevitably hit memory limits. To handle 1,000+ units, the engine must adopt Data-Oriented Design principles, often implemented via an Entity Component System (ECS).4.1. Memory Layout: SoA ImplementationThe primary goal is maximizing CPU cache usage. In a standard update loop, the CPU loads a cache line (typically 64 bytes). If a unit object is large (e.g., 256 bytes), the CPU must load multiple lines for a single unit, filling the cache with useless data.In the Structure of Arrays (SoA) approach, data is split into component arrays:C++struct UnitData {

&nbsp;   std::vector<Vector3> positions;   // Stream 1: Positions

&nbsp;   std::vector<Vector3> velocities;  // Stream 2: Velocities

&nbsp;   std::vector<int> targetIDs;       // Stream 3: Targets

&nbsp;   std::vector<float> health;        // Stream 4: Health (Not loaded during movement update)

};

When the Movement System runs, it iterates only over the positions and velocities arrays. The CPU loads a cache line containing position data for 4-5 units at once. This drastically reduces cache misses and allows the compiler (or developer) to use SIMD instructions (\_mm\_add\_ps in SSE/AVX), processing 4 or 8 vectors in a single instruction cycle. This provides the multiplicative performance gain needed for mass scale.4.2. Job System and MultithreadingSingle-threaded performance is insufficient for 1,000+ units. Logic must be parallelized. Implementation Details and Edge CasesOptimizing code is not just about raw speed, but also "game feel" and robustness. "Current code" likely misses specific RTS phenomena, leading to bugs and player frustration.5.1. The "Harvester Hack" (Collision Layers)A common logical problem is congestion at resource collection points. If workers (harvesters) fully collide with each other, resource income halts due to traffic jams. StarCraft solves this with a specific state exception: units carrying resources ignore collisions with other workers.24Recommendation: Implement collision layers/masks.Layer 1: Combat Units (collide with everything).Layer 2: Workers (collide with Combat, ignore Workers when carrying load).Layer 3: Air Units (ignore Ground).This simple logical change radically reduces local avoidance calculation complexity in high-density economic zones.5.2. Stuck DetectionWith thousands of units, some will inevitably get stuck in geometry or deadlocks. A robust system requires "Stuck Breaker" logic 25:Metric: Track DistanceTraveled over TimeWindow.Trigger: If Speed > 0 (unit trying to move) but DistanceTraveled < Threshold, the unit is stuck.Resolution:Soft: Recalculate path with a temporary penalty on the current tile (force A\* to find a new route).Hard: Teleport ("nudge") the unit slightly toward a valid neighbor.Emergency: If a unit is stuck inside a building footprint (e.g., constructed on top of it), apply a massive expulsion force to eject it.35.3. Group Cohesion and FormationsUnits moving via flow fields tend to stretch out or bunch up. To maintain RTS-style formations, group logic must be introduced:Flocking Forces: Add a "Cohesion" force to steering behaviors that pulls units toward the centroid of their selection group.5Arrival Logic: A logical flaw in A\* is that 100 units trying to reach point (x,y) will fight for the exact center.Solution: Use arrival "sidedness." As units arrive, they register as static obstacles. The flow field naturally routes subsequent units around them. Alternatively, implement "offset targets," where the group command calculates unique destination slots for each unit in a formation pattern before movement begins.3Section 6. Emergent Complexity and Gameplay ConsequencesDeep analysis suggests that "perfect" pathfinding is not always the ultimate goal. Successful RTS games (StarCraft, Brood War) use pathfinding limitations as gameplay mechanics.6.1. Predictability vs. IntelligenceHigh-level players prefer Predictability over Intelligence. If a unit "smartly" avoids danger by taking an unexpected route, it frustrates the player's tactical intent.Insight: Flow field vector generation must be deterministic. Units should not "improvise." Stuck logic (teleport/slide) is often preferable to complex disentanglement logic, as it is more predictable for a player expecting instant feedback.266.2. The "Deathball" PhenomenonAdvanced pathfinding (like the flocking in StarCraft II) leads to units stacking perfectly, maximizing fire density ("Deathball"). Conversely, "clunky" pathfinding in Brood War forced units to spread out, creating natural concave formations.Design Decision: If tactical depth is the goal, you might intentionally limit turn radius or increase separation weight in ORCA to force unit spreading, effectively "worsening" pathfinding to improve the meta-game.266.3. Flow Field as AI MapThe Cost Field used for pathfinding can be utilized for AI analysis.Influence Maps: The Integration Field (heat map) tells the AI where "chokepoints" are (areas where flow vectors converge).Tactical AI: The AI can use the flow field to detect incoming enemy reinforcement directions, placing turrets exactly on high-flow vector paths.1ConclusionOptimizing an RTS for 1,000+ units is not solved by simply tuning A\* heuristics; it requires a fundamental architectural shift. The "current code" likely suffers from $O(N^2)$ interactions of object-oriented actors and inefficient memory usage. The solution lies in decoupling Macro-Navigation (Flow Fields) from Micro-Navigation (ORCA/Steering) and backing both with a Data-Oriented memory layout.By treating the map as a flow generator and units as particles in that flow, the system shifts computational complexity from the number of units to the size of the active map area. This decoupling is the key insight that allowed games like Supreme Commander 2 to seamlessly simulate massive armies. Implementing hierarchical flow fields combined with ECS-based RVO2 will provide a 1-2 order of magnitude performance boost compared to legacy A\* approaches, transforming the system from a bottleneck into a scalable foundation for large-scale strategic gameplay.
