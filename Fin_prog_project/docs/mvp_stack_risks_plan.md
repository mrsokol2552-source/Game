# MVP, Stack, Risks, Order

## Цель

Собрать первый рабочий контур проекта, который:

1. раз в 30 минут получает рыночные данные;
2. вычисляет простые триггеры движения и всплеска волатильности;
3. при событии сохраняет `evidence.json`;
4. запускает `codex exec` для текстовой аналитики;
5. отправляет результат в тестовый канал доставки;
6. оставляет воспроизводимый лог каждого шага.

## Что считаем MVP

MVP не должен пытаться решить весь проект сразу. Достаточно следующего набора:

- Источник данных: MOEX ISS в JSON-режиме.
- Инструменты первой очереди: `USDRUB_TOM`, `CNYRUB_TOM`, один контракт Brent-прокси, один контракт gold-прокси.
- Триггеры: `|delta_pct| >= 1%` и `vol_short / vol_long >= k`.
- Хранилище: локальные JSON-файлы + SQLite для истории.
- Аналитика: доходности, волатильность, простая rolling-регрессия или ridge без перегруза SARIMAX на первом этапе.
- Генерация текста: только через `codex exec`, без UI-автоматизации VS Code.
- Доставка: Playwright persistent session в тестовый чат.
- Операционка: структурные логи, cooldown, повторные попытки и ручная диагностика.

## Рекомендуемый стек

### Этап 1: быстрый боевой MVP

- Язык: Python 3.12+.
- HTTP: `httpx`.
- Данные и расчеты: `pandas`, `numpy`.
- Модель первой очереди: `scikit-learn` для ridge/linear regression.
- Валидация схем: `pydantic`.
- Доставка: `playwright`.
- Хранилище: встроенный `sqlite3` + файловые snapshots.
- Конфиг: JSON.
- Тесты: `pytest`.

Причина выбора: для первого контура Python быстрее даст рабочий pipeline, чем .NET, а главный риск у нас интеграционный, а не вычислительный.

### Этап 2: усиление эксплуатации

- Если MVP стабилен, можно оставить Python как основной runtime.
- Если появится требование к сервисному режиму Windows, richer UI и строгому деплою на одной машине, можно отдельно рассмотреть перенос фонового worker-слоя на .NET.

Сейчас миграцию в .NET делать рано. Сначала нужно доказать, что связка `данные -> триггер -> evidence -> codex -> delivery` устойчива.

## Основные риски

- Данные ISS могут быть с задержкой и без части рыночной глубины.
- Реальные коды контрактов Brent и золота надо закрепить до начала кодинга, иначе сборщик будет нестабилен.
- Связь нефти/золота с валютами режимозависима, поэтому модель нельзя продавать как надежный предсказатель.
- `codex exec` зависит от локальной среды, авторизации и доступности CLI.
- Автоматизация Яндекс.Мессенджера остается самым хрупким техническим участком.
- Без cooldown и контроля качества проект быстро начнет спамить ложными сигналами.

## Порядок реализации

### Фаза 0. Зафиксировать входные допущения

- Подтвердить список инструментов и конкретные тикеры MOEX.
- Зафиксировать базу сравнения для `±1%`: прошлый опрос или последний сигнал.
- Определить, какой канал доставки считается основным, а какой резервным.
- Зафиксировать минимальный формат аналитического сообщения.

Выходной критерий: есть короткий документ с неизменяемыми входными правилами первой версии.

### Фаза 1. Каркас проекта

- Поднять структуру каталогов.
- Сделать `README`, карту проекта, файл с рисками и поэтапный план.
- Подготовить шаблон конфига и схему логирования.

Выходной критерий: каталог готов к разработке, роли папок и документов не спорят друг с другом.

### Фаза 2. Сбор и сохранение данных

- Реализовать клиент MOEX ISS.
- Научиться стабильно получать последние значения и короткую историю.
- Сохранять сырой ответ и нормализованные записи локально.

Выходной критерий: по одной команде получается валидный snapshot рынка без ручных действий.

### Фаза 3. Аналитический движок

- Считать доходности и проценты изменения.
- Реализовать детект `±1%`.
- Реализовать `vol_short`, `vol_long`, `vol_ratio`.
- Добавить cooldown и базовую проверку качества данных.

Выходной критерий: движок умеет детерминированно говорить, есть событие или нет.

### Фаза 4. Evidence и prompt pipeline

- Зафиксировать JSON-схему `evidence.json`.
- Собрать prompt builder с жестким шаблоном.
- Поднять раннер `codex exec` с контролем stdout, stderr и таймаутов.

Выходной критерий: из локального snapshot получается воспроизводимый текстовый отчет.

### Фаза 5. Доставка

- Настроить Playwright persistent context.
- Снять реальные локаторы через codegen.
- Реализовать отправку в тестовый чат, повторную попытку и диагностический скриншот на ошибке.

Выходной критерий: система сама доставляет тестовое сообщение в выбранный канал.

### Фаза 6. Эксплуатация

- Добавить планировщик запуска.
- Добавить health-check и файловый журнал событий.
- Вынести конфиг в отдельный JSON.
- Провести dry-run на нескольких торговых циклах.

Выходной критерий: проект можно оставить работать фоном и понимать, что произошло при любой ошибке.

## Узкие места, которые нельзя игнорировать

- Контракты Brent и золота нужно заранее проверить на стабильность кодов и сессионность.
- Надо рано решить, допускаем ли мы задержанные данные ISS как норму.
- Текстовую аналитику нужно строить только на `evidence.json`, иначе поведение будет плохо воспроизводимо.
- Доставку лучше проектировать так, чтобы позже можно было заменить Playwright на официальный API без переписывания всего пайплайна.

## Ближайший практический следующий шаг

Начинать нужно не с UI и не с прогнозной модели. Следующий реальный шаг:

1. создать `config/appsettings.json`-шаблон;
2. описать схему `evidence.json`;
3. сделать минимальный fetcher MOEX ISS;
4. собрать локальный dry-run без Codex и без мессенджера.

Если этот этап не держится, остальная часть проекта будет только маскировать проблему.
