# Bottlenecks And Solutions

## Назначение

Этот файл фиксирует не только возможные узкие места проекта, но и конкретные решения, которыми мы будем их снимать по мере реализации.

## Реестр узких мест

### 1. Не зафиксированы реальные торговые инструменты

Проблема:
Без точных тикеров и режима торгов нельзя стабильно писать fetcher и тесты.

Решение:
- До начала кодинга закрепить список инструментов первой версии.
- Для каждого инструмента сохранить источник, код, валюту котировки и тип цены.
- В конфиге разделить логическое имя инструмента и фактический MOEX symbol.

### 2. ISS может отдавать данные с задержкой

Проблема:
Триггеры будут корректными математически, но поздними относительно рынка.

Решение:
- Сразу считать MVP работающим на delayed-данных.
- В каждом сообщении указывать источник и возможную задержку.
- Вынести режим real-time как отдельное усиление, а не как условие старта проекта.

### 3. Непрозрачная база сравнения для триггера ±1%

Проблема:
Без этого условие сигнала будет все время дрейфовать и спорить само с собой.

Решение:
- Зафиксировать один режим для v1: сравнение с предыдущим опросом.
- Отдельно предусмотреть режим сравнения с последним сигналом.
- Параметр базы сравнения вынести в конфиг.

### 4. Сессионность рынка и окна истории

Проблема:
Ночной разрыв, выходные и неравномерные торговые периоды ломают волатильность и короткие модели.

Решение:
- Нормализовать временную шкалу до четких 30-мин интервалов.
- Пустые интервалы помечать как пропуски, а не выдумывать значения.
- В расчетах качества модели хранить число валидных наблюдений на окне.

### 5. Хрупкая JSON-схема evidence

Проблема:
Если структура `evidence.json` будет меняться без контроля, prompt и downstream-логика быстро развалятся.

Решение:
- Ввести одну каноничную схему файла.
- Версионировать схему полем `schema_version`.
- Валидировать `evidence.json` до запуска `codex exec`.

### 6. Слишком ранняя попытка строить “умный прогноз”

Проблема:
Есть риск потратить много времени на модель, пока еще не доказана устойчивость данных и доставки.

Решение:
- Для v1 использовать простую и интерпретируемую модель.
- Считать прогноз вторичным слоем поверх рабочего мониторинга.
- SARIMAX и более сложные методы отложить до появления стабильной истории и метрик ошибок.

### 7. Низкая воспроизводимость текста от Codex

Проблема:
Если prompt зависит не только от файла фактов, аналитика начнет гулять между запусками.

Решение:
- Строить prompt строго из `evidence.json` и фиксированного шаблона.
- Убрать из первой версии любые внешние источники в момент генерации.
- Сохранять prompt рядом с `evidence.json` для аудита.

### 8. Зависимость от локального состояния Codex CLI

Проблема:
`codex exec` может не стартовать из-за авторизации, среды, таймаутов или изменений в локальной установке.

Решение:
- Сделать отдельный preflight-check для CLI.
- Проверять доступность команды, авторизацию и базовый dry-run до первого боевого цикла.
- Ошибку Codex не считать падением всего приложения: событие должно логироваться и ждать следующего цикла.

### 9. Автоматизация Яндекс.Мессенджера через браузер нестабильна

Проблема:
DOM меняется, возможны капча, повторный логин и блокировки headless-режима.

Решение:
- Работать через persistent context и headful-режим на старте.
- Снимать локаторы через Playwright codegen, а не вручную из DevTools на глаз.
- На ошибке сохранять screenshot и trace.
- Сразу проектировать слой доставки как адаптер, чтобы позже заменить Playwright на API.

### 10. Возможен спам сигналами

Проблема:
Даже рабочая математика без антидребезга быстро превратится в поток шумовых уведомлений.

Решение:
- Добавить cooldown по инструменту.
- Добавить минимальный порог повторного сигнала.
- Лимитировать количество уведомлений за окно времени.

### 11. Слабая наблюдаемость в фоне

Проблема:
Если задача запускается по расписанию и молча падает, проект выглядит “работающим”, хотя он уже сломан.

Решение:
- Вести структурные логи по каждому этапу контура.
- Логировать начало и конец каждого цикла.
- Для каждого сбоя писать причину, шаг и путь к артефакту.
- Добавить файл последнего успешного прогона.

### 12. Смешение проектных решений и черновиков

Проблема:
Если решения будут жить только в чате или в случайных заметках, план быстро станет несогласованным.

Решение:
- Все принятые решения фиксировать в `docs/`.
- Отдельно хранить общий поэтапный план и отдельный реестр узких мест.
- Не плодить дублирующие markdown-файлы с одинаковой ролью.

## Порядок снятия узких мест

Сначала снимаем блокеры, без которых нельзя вообще начать разработку:

1. реальные инструменты и формат данных;
2. база сравнения для сигнала;
3. схема `evidence.json`;
4. preflight для `codex exec`;
5. тестовый сценарий доставки.

После этого снимаем эксплуатационные риски:

1. cooldown и ограничение спама;
2. логирование и health-check;
3. traces/screenshots для браузерного слоя;
4. оценку качества модели и пометку уровня уверенности.

## Правило проекта

Если появляется новое узкое место, его нужно не просто перечислить, а сразу добавить сюда вместе с конкретной стратегией решения или обхода.
